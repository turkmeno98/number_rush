## Расчётная проверка экономики

В `analysis/` сохранены две редакции моделей и JSON-результаты. Во v0.2: полный перебор 10 млн комбинаций, 90 тыс. независимых сессий, 12 проверок верхней границы EV, пять границ крафта, 44 примера правил. Это не Lua/Roblox-тесты, не рыночная симуляция всего мира и не доказательство всех отказных свойств.

Архивный расчёт может регенерировать свой локальный отчёт; авторитетным текстом остаётся `docs/BALANCE_V02.md`.

## Проверки снимка репозитория

`python3 tools/verify_snapshot.py` проверяет JSON дерева, наличие требуемых классов/скриптов/RemoteEvent, исключение диагностических скриптов, целостность исходников внутри `.rbxlx`, уникальность 12 кодов и суммы весов. Runtime Luau в этом окружении не исполнялся; импорт `.rbxlx` в Studio отдельно ещё не подтверждён.

## Следующие ручные проверки

1. Перезапуск после одной платной выдачи: баланс и предмет сохранены, sequence не сброшен.
2. Повтор того же sequence не списывает деньги второй раз; старый sequence после следующей выдачи не запускает новый платёж.
3. Двойное нажатие, смена оператора во время анимации, недостаток денег, 25/25 мест.
4. Два сервера одновременно резервируют один полный номер: только один владелец.
5. Аварийное завершение после каждого этапа журнала: следующий вход восстанавливает согласованное состояние.
6. Неизвестный результат записи не вызывает автоматический второй номер/возврат.
7. Задержка API дольше 60 секунд: UI не делает новый запрос самостоятельно.
8. После установки/продажи — отдельные проверки дохода, лимитов и освобождения реестра.

Для отказных тестов использовать отдельные тестовые профили и номера. Не менять общие имена хранилищ и не включать BalanceSaveTest без понимания, какой баланс он перезаписывает.
